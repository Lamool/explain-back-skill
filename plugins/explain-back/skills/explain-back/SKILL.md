# explain-back — 배운 것 되짚기

작업을 "끝냈다"에서 "이해했다"로 넘어가게 돕는다. 이번 작업에서 실제로 쓰인 개념을 골라 정리하고, 사용자가 스스로 설명해 보게 한다. 남이 써 준 설명을 읽는 것보다 직접 떠올려 답해 보는 것이 훨씬 오래 기억에 남기 때문이다.

## 입력 받기
입력: $ARGUMENTS

1. 입력이 있으면 그 주제나 범위(파일, 기능, 개념 이름)에 집중한다.
2. 입력이 비어 있으면 이번 대화에서 한 작업 전체를 대상으로 한다. 대화만으로 부족하면 `git diff`, `git log -5`, 최근 수정한 파일을 확인한다.
3. 정리할 작업이 없으면 "어떤 작업을 되짚어 볼까요? 파일이나 주제를 알려주세요" 라고 묻고 멈춘다.
4. 프로젝트 루트에 `LEARNING.md` 가 있으면 먼저 읽는다. 이미 다룬 개념은 반복하지 않는다. 대신 그 개념을 한 단계 더 깊이 다루거나, 지난번에 틀린 개념을 다시 확인하는 데 활용한다.

## 1단계: 핵심 개념 3개
이번 작업에서 **실제로 쓰였고, 다음 작업에도 다시 쓸** 개념을 3개 고른다.

고르는 기준:
- 이 작업에만 해당하는 구체적인 개념을 고른다. "변수", "함수"처럼 너무 일반적인 개념이나, 이번 작업과 상관없는 교과서 내용은 고르지 않는다.
- 사용자 수준에 맞춘다. 대화에서 이미 능숙하게 다룬 것보다 처음 등장했거나 헷갈려 한 것을 우선한다.
- 문서 작업이라면 글쓰기 개념(독자 설정, 결론 먼저 쓰기, 표와 문장 중 무엇을 쓸지)도 개념이 될 수 있다.

개념마다 아래 형식으로 쓴다.

```
### 1. [개념 이름]
- **한 줄 정의**: 쉬운 말로 한 문장.
- **이번 작업에서는**: 어디에 어떻게 쓰였는지. 코드라면 `파일경로:줄번호` 를 붙인다.
- **왜 중요한가**: 이걸 모르면 어떤 실수를 하는지, 또는 흔히 하는 오해가 무엇인지.
```

## 2단계: 확인 퀴즈 (대화형)
개념마다 1문제씩, 총 3문제를 낸다. 단순 암기보다 이해를 확인하는 문제가 좋다. 가능하면 세 문제의 유형을 섞는다.

난이도는 쉬운 문제에서 어려운 문제 순서로 올린다. 첫 문제부터 막히면 나머지도 통째로 넘기기 쉽고, 쉬운 문제로 한 번 답해 보면 다음 문제에도 도전할 마음이 생기기 때문이다.

- **Q1 (쉬움)**: 코드나 문서를 보면 바로 답할 수 있는 문제. 예: "7번 줄의 반복은 언제 끝나나요?"
- **Q2 (중간)**: 한 단계 생각해야 하는 예측하기나 틀린 곳 찾기 문제.
- **Q3 (응용)**: 다른 상황에 적용하는 문제. LEARNING.md 에 복습할 개념이 있으면 여기서 엮는다.

| 유형 | 예시 |
|------|------|
| 설명하기 | "이 함수에서 `return` 을 빼면 호출한 쪽은 무엇을 받게 되는지 설명해 보세요." |
| 예측하기 | "`app.py:42` 의 조건을 `>=` 로 바꾸면 결과가 어떻게 달라질까요?" |
| 적용하기 | "다른 프로젝트에서 같은 문제가 생기면 무엇부터 확인하겠어요?" |
| 틀린 곳 찾기 | 짧은 코드나 문장을 보여 주고 어디가 문제인지 묻는다. |

문제를 낸 뒤에는 **정답이나 힌트를 쓰지 말고 여기서 응답을 끝낸다.** 사용자가 직접 떠올려 보는 과정이 이 스킬의 핵심이다. 마지막에 "편하게 답해 보세요. 모르겠으면 '패스'라고 하면 힌트를 드릴게요." 라고 덧붙인다.

## 3단계: 힌트 (패스한 문제만)
"패스"나 "모르겠어요"라고 한 문제에는 바로 정답을 보여 주지 말고 **힌트를 하나** 준 뒤 한 번 더 답할 기회를 준다. 정답을 읽는 것보다 힌트를 받고 스스로 떠올리는 쪽이 훨씬 오래 기억에 남기 때문이다.

- 힌트는 답을 직접 말하지 않고, 생각할 출발점만 준다. 예: "`while True` 에서 `True` 는 언제 거짓이 될까요?", "오류가 난 줄의 변수 이름을 위에서 만든 이름과 한 글자씩 비교해 보세요."
- 여러 문제를 패스했으면("다 패스") 패스한 문제의 힌트를 한 번에 모아서 준다.
- 답한 문제는 이 단계에서 채점하지 않는다. 힌트를 받은 문제의 답이 오면 모두 함께 채점한다.
- 힌트를 받고도 다시 패스하거나, 사용자가 "정답 알려줘"라고 하면 바로 4단계로 넘어가 모범 답안을 보여 준다.
- 패스한 문제가 없으면 이 단계를 건너뛴다.

## 4단계: 채점과 피드백
사용자가 답하면 문제마다 채점한다.

- **결과**: 정답 / 부분 정답 / 다시 보기 중 하나.
- **피드백**: 맞은 부분은 구체적으로 인정한다. 빠지거나 틀린 부분은 무엇이 왜 다른지 1~3문장으로 짚는다.
- **모범 답안**: 짧게 쓴다.
- 힌트를 받고 맞혔으면 결과는 그대로 정답이나 부분 정답으로 매기고, 기록할 때 결과 뒤에 `(힌트)`를 붙인다.

말투는 시험 감독관이 아니라 같이 공부하는 선배처럼 한다. "패스"나 "모르겠어요"는 틀린 답이 아니라 복습할 곳을 찾은 것으로 다룬다. 사용자가 답 대신 추가 질문을 하면 먼저 질문에 답하고, 그다음 퀴즈로 돌아간다.

## 5단계: LEARNING.md 에 기록
채점이 끝나면 프로젝트 루트(git 저장소라면 저장소 루트, 아니면 현재 작업 폴더)의 `LEARNING.md` 맨 끝에 추가한다. 파일이 없으면 `# 학습 노트` 제목으로 새로 만든다. UTF-8 로 쓰고, 기존 내용은 절대 덮어쓰지 않는다.

```markdown
## YYYY-MM-DD · [파일명 (파일이 없으면 작업 주제)]

**핵심 개념**
- **[개념 1]**: 한 줄 요약
- **[개념 2]**: ...
- **[개념 3]**: ...

**퀴즈**
| 문제 | 정답 | 결과 |
|------|------|:----:|
| [문제를 한 문장으로] | [모범 답안 핵심 한 줄] | O |
| ... | ... | △ |
| ... | ... | X |

**복습**
- [△·X 였던 내용을 짧게]

---
```

나중에 훑어보기 쉽게 짧게 쓰는 것이 목적이다.
- 네 부분(날짜와 파일명 / 핵심 개념 / 퀴즈 / 복습)을 이 순서로 모두 쓴다.
- 핵심 개념은 개념마다 한 줄, 20자 안팎으로 쓴다. 줄 번호는 쓰지 않는다.
- 퀴즈 표에는 실제로 낸 문제와 모범 답안을 함께 적어서, 이 파일만 보고도 다시 풀어 볼 수 있게 한다. 코드는 `isinstance(x, str)`처럼 짧은 것만 넣고, 표가 깨지지 않게 `|` 문자는 쓰지 않는다.
- 결과는 `O`(정답) / `△`(부분 정답) / `X`(다시 보기) / `-`(미응시)로 쓴다. 힌트를 썼으면 `X (힌트)`처럼 뒤에 붙인다.
- 모두 `O`이면 복습에 `- 없음`이라고 쓴다.
- 외부 파일 상태처럼 남겨 둘 메모가 있으면 복습 목록 끝에 `- 참고: ...`로 한 줄만 추가한다.

기록한 뒤 "LEARNING.md 에 저장했어요." 라고 한 줄로 알린다. 사용자가 퀴즈를 끝까지 하지 않고 다른 작업으로 넘어가면, 낸 문제와 정답은 그대로 기록하고 결과에는 `-`(미응시)를 쓴다.

## 말투와 규칙
- 친근한 존댓말(`~요`, `~해요`)을 쓴다. 이모지는 쓰지 않는다.
- 기술 용어는 원문 그대로 쓰고, 처음 나올 때만 짧게 풀어 준다.
- 코드는 필요한 몇 줄만 인용한다. 긴 코드를 통째로 다시 보여 주지 않는다.
- 개념 정리는 한 화면 안에 들어오게 짧게 쓴다. 더 깊이 알고 싶으면 사용자가 물어볼 것이다.
